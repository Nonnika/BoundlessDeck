# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

BoundlessDeck is an infinite-canvas workbench (local file links/previews, code, terminals) written in pure Go on **MyGo** (`github.com/egoist/mygo`, pinned in `go.mod`). The UI is native: MyGo's `ui` package draws it directly — no WebView page, no npm, no JS bindings. The project used to be a Vite/TypeScript web frontend; that was removed on purpose, so don't reintroduce it. macOS 13+ (terminals use libghostty-vt).

Product/architecture docs (Chinese): `docs/requirements.md` (v0.2 native architecture, requirement IDs and status, verified MyGo API references) and `docs/agent-workbench.md` (v0.3 agent-driven product requirements).

## Commands

The `Makefile` wraps these (`make` lists its tasks; `make check` = fmt-check + vet + test before a commit).

```sh
go tool mygo dev ./app                                   # run in dev mode; restarts on .go changes
go tool mygo build ./app                                 # package into build/<os>-<arch>/ (config in app/mygo.json)
go test ./...                                            # canvas + persistence unit tests, headless (no window)
go test -race ./...
go test -run TestZoomKeepsThePointUnderThePointer ./app  # single test
go tool mygo vet ./app                                   # build-time lifecycle checks for native UI (stored elements, goroutine captures)
DECK_SNAPSHOT=1 go test -run TestSnapshot ./app          # re-render docs/canvas-snapshot.png
```

When changing UI code, also follow `.agents/skills/mygo-maintenance/SKILL.md` (MyGo lifetime/identity/threading rules; it suggests `CGO_ENABLED=0 go test ./...` too). Check APIs against the pinned MyGo source: `go list -m -f '{{.Dir}}' github.com/egoist/mygo`.

## Terminology

Every element on the deck is a **block** (note, file, terminal… are block *kinds*). Never name things `node` or `card` in code; the data file key is `"blocks"`.

## Architecture

The app is one `package main` in `app/`, with its `mygo.json` and `resources/` (Go keeps a package's files in one directory, and the block kinds, canvas and MCP tools are all methods on `*deck`, so they stay together). Self-contained parts live in `internal/` at the repository's root, each with its tests:

- `internal/word` — Word → Markdown (below); `internal/word/wordtest` builds a .docx for tests.
- `internal/pdf` — PDF pages (below); `internal/pdf/pdftest` writes PDFs for tests.
- `internal/chart` — the 图表's table and drawing (below).
- `internal/icons` — the toolbar icons (Lucide), `icons.Note`, `icons.Chart`…

The root keeps the module (`go.mod`), docs and `internal/`. In `app/`:

- `main.go` — creates the `app`, opens the window with `ui.View(a.view)`, wires file drop and save-on-close.
- `menu.go` — the menu bar: every command with its shortcut (new blocks ⌘N/⇧⌘N/⇧⌘O/⌘T/⇧⌘B/⇧⌘G/⇧⌘K, delete ⌘D, zoom ⌘0/⌘=/⌘-, open folder ⌘O, home ⇧⌘H) and 帮助 → 键盘快捷键 (⌘/; off macOS MyGo hides `RoleHelp` and its submenu, so `menuForMac` false puts a plain 帮助 and a 设置 item clicked straight on the bar), which opens a window (`shortcuts.go`) listing every menu item with keys, read from the menu itself (`menuShortcuts`), and the canvas's keys and gestures (`gestureGroups`; no accelerators for those: they would take space/arrows from the canvas). On macOS the menu takes its keys before the window, so its `Click` runs (via `win.Update`); the window's `c.Shortcut`s are the same commands, for tests. A block added by shortcut lands under the mouse (`addAtPointer`: `Screen.CursorScreenPoint` minus `ContentBounds`, `cursorIn`), the view's middle when the mouse is outside.
- `home.go` — `app`: the home screen (open a folder, recent folders kept in `recents.json` in MyGo's user-data dir) or the `deck` of the folder open. Each deck is a folder; switching decks, going home or closing the window keeps the state of each terminal the user typed or pasted into (`runtime.termUsed`; one left alone keeps what its block had) in its block (`termstate.go`: `History()` of what it showed, at most 256 KB, and the shell's dir, saved in deck.json as `term`), saves the deck and hangs the shells up — nothing keeps running. Opened again, a terminal block starts a new shell in that dir with the old output fed in above it under a dim "已恢复" line. A terminal that finishes starting after its block was hung up closes itself (`runtime.termGen`).
- The deck's top-left pill (`homePill` in `canvas.go`, a `ui.Toolbar` so its buttons have no face until hovered): back home, and the workspace's name, a `ButtonBase(...).Menu(workspaceMenu)` listing the folders opened lately (`d.workspaces` = `app.recentPaths`, this one checked) to switch to (`d.onOpen` = `beginOpen`)and 打开文件夹… (home is the back button).
- `homescene.go` — the home screen's background: one dotted canvas plane leaning back in 3D (`Element.Transform` + `Perspective`), blocks on it blurred by depth (`Element.Blur`: near blurry, far sharp; only ≥ 960 wide), the deck mark. The scene and the column are both `Absolute` (absolute elements paint above in-flow siblings). Render with `DECK_SNAPSHOT=1 go test -run TestHomeSnapshot ./app`
- `memo.go` — the 笔记 block (`kindMemo`, `"memo"`): a Markdown file of the deck's folder, made by the toolbar (`newMemo` → `笔记.md`, `笔记 2.md`…). It shows rendered in a live preview (`livePreview` in `sticky.go`, shared with QuickLook): unfocused, the `bodyCover` lies over it and a pan moves the canvas; a click focuses it and the wheel scrolls it (its page takes the wheel itself into `rt.liveScroll`, since handlers get it before a `ui.Scroll` does); a click on the focused preview edits it in a `TextArea` (`editBody`), and Esc/⌘↵ ends the edit with the preview still focused. Edits are written back to the file once typing rests (800 ms), when the edit ends and when the block is hung up (`flushMemo`); while shown, its file is checked every 2 s and read again if something else wrote it. Its title is the file's name: renaming the block renames the file (never over another). Removing the block leaves the file. Not to be confused with `kindNote` (QuickLook sticky note, text kept in deck.json, and passing: see `lifespan.go`). Through the MCP, `text` on a memo writes its file; `mcpApplyField` takes `dry` so validation touches no file. Every kind is listed once, in `blockKinds`.
- `stack.go` — the 块堆 block (`kindStack`, `"stack"`): a wallet of blocks. Dragging a block onto a stack puts its ID in the stack's `items` and hides it from the canvas (it stays in `d.blocks`, keeps its data, and its terminal/browser is hung up until taken out). Its cards stand like a wallet's, headers peeking out (`stackGeom`); a face holding Markdown (QuickLook, 笔记, .md/Word) shows it rendered (`stackFaceMarkdown`), in a clipped child over the painted card, so the pill and scrollbar paint in `DrawOver`. A click opens it (`d.stackOpen`): hovering its middle pushes the card under the pointer out (the cards after it make room, it rises; springs keyed by card ID), hovering its top/bottom edge or the wheel scrolls the cards (`stackScroll`), and losing the selection or the card's focus puts the card back (`watchStack`). Space opens a long preview in the window with the card's content (`openStackPreview`): it grows out of the card's place (`d.previewFrom`, from the pile's `Bounds()`; the panel is laid out once at its size and scaled/moved), the other cards move apart (`stackSpreadAnim`), and closed (`closeStackPreview`) it shrinks back (`d.previewLeaving`) before the card shows again; it shows just the card's icon, title and content, turned by ←/→, closed by space/escape/a click on the backdrop. Holding a card's top-right corner (its kind label, `pluckCornerW`) for `pluckHold` plucks it out (`stackpluck.go`, `d.pluck`): its header stripe fills meanwhile (the hold is an `AnimateTo` keyed per press), then it follows the pointer as a ghost the size of its block (`pluckView`, over the canvas); let go over the canvas it is taken out there (`stackTake`), over another stack it moves in, over its own or with Esc it goes back. The stack's card handler routes the press's moves/release to `pluckInput`. Membership changes go through `changeStack` (before/after items), so ⌘Z undoes the whole stack edit. A stack never holds another stack.
- `chart.go` — the 图表 block (`kindChart`, `"chart"`): its glue to the deck; the table and its drawing are `internal/chart`. A chart of the table in its `Text` (rows of `名称, 数值…`, cells parted by tabs, else commas/semicolons, or a Markdown table; a first row with a non-number names the series; `chart.Parse`, cached in `rt.chart` by its source, `d.chartDataOf`). `block.Chart` (MCP field `chart`) is how it draws: `chart.Types` bar/hbar/line/area/pie, empty is bar (`chart.Of`). Drawn by the painter (`chart.View.Draw`): categorical hues in a fixed order (at most 8 series; a pie folds past 8 into 其他), round axis steps (万/亿 ticks), bars ≤ 24 px with a rounded data end, 2 px lines, a legend for ≥ 2 series, a hovered category/slice gets a tooltip. The header holds a type chip (native menu, `chartMenu`) and a table button; it or a double click edits the table in a `TextArea` beside the chart (under it when narrow), which follows live. In a 块堆 its face is the chart, `Compact`.
- `lifespan.go` — a QuickLook block goes by itself: `block.Expires` (Unix ms, 0 keeps it; MCP fields `expires` and the derived `ttlMinutes`, minutes from now — `mcpField.Derived` marks a field kept in no block), an hour after it is made by default. Its header shows the time left (`lifeChip`); a click pops up spans to pick (`lifeMenu`, counted from then, or 永久保留). It fades over its last `noteFade`; `expireNotes` (each frame of the view, which asks for the next frame when something will change) removes it through `removeBlock`, so ⌘Z brings it back with `noteRescue` left — never while it is edited. Ones that ran out while the deck was closed are dropped on load (`dropExpired`). Time comes from `d.now()` (`d.clock` in tests).
- `termstate.go` — what a terminal block keeps of its terminal across closing the deck (history + dir), and where its next shell starts.
- `deck.go` — state and model: `deck` (camera, blocks, selection, drag/pan/marquee state, undo/redo stacks), `block` (serialized, world coordinates), `runtime` (per-block non-persisted state: loaded text, `editor.State`, bitmap, `terminal.Terminal`), camera math (`toScreen`/`toWorld`/`zoomAt`), add/remove/undo/redo, and `deck.json` load/save.
- `canvas.go` — the per-frame view: grid, canvas input (pan/zoom/marquee), block input (select, title-bar drag), toolbar, status bar, fit-all.
- `blocks.go` — one block's view and its body per kind (text via `ui/editor`, image, terminal via `plugins/terminal`), plus off-thread loaders. Images that may be see-through (PNG alpha/tRNS, WebP alpha, SVG) show on a checkerboard.
- `preview.go` — how a file block previews by extension (`previewOf`): `.md` and Word rendered with `ui/markdown` in a scroller (a `hasScroller` body), PDFs a page at a time with a ‹ n / N › pager (`block.Page` is saved), re-rendered in 256 px steps as the zoom changes. Controls inside a block body must take presses with their own `HandleInput`: the card's handler takes them before a `ui.Button`.
- `browser.go` — the browser block (`kindBrowser`, `block.URL` saved): a native `ui.WebView` under a bar (back/forward/reload/address). The page zooms with the canvas via `Page.SetZoomFactor(cam.S)`, but only once the zoom rests: WebKit's page zoom re-lays out and redraws, lagging behind the block, so while the canvas zooms the page shows as a `CapturePage` snapshot scaled with the block (`zoomPage`; held at its old size until the snapshot arrives), and the live page returns after it has redrawn at the new zoom; pages are `Untrusted`, which alone would block every cross-origin navigation (even a redirect such as www.bing.com → cn.bing.com), so an `OnWillNavigate` listener allows web schemes (`webScheme`) and the web view starts blank and loads its URL only after the listeners are on; a user-clicked new-window link opens a browser block beside it. The card *and* the canvas decline presses in a browser's body (`inBrowserBody`) so its `ui.Button`s and `TextInput` get them; the `bodyCover` starts below the bar. In tests there is no window, so the page shows `errNoWindow`.
- `internal/pdf` — PDF pages rendered by CoreGraphics through purego (no cgo, `pdf_darwin.go`); `pdf_other.go` stubs it elsewhere. `pdf.Open` → `*pdf.Doc`.
- `mcp*.go` — the workspace's MCP endpoint (see "MCP" below). `mcpschema.go` is the single source of the block field table; `mcpdeck.go` validates patches and shapes results; `mcplayout.go` aligns, distributes and arranges blocks (`align_blocks`, `distribute_blocks`, `arrange_blocks`), computing targets first so `applyPlacements` records one undoable move; `mcpserver.go` serves JSON-RPC tools/resources on a Unix socket in `.boundlessdeck/`, scheduling every deck access on the UI thread; `mcpworkspace.go` writes `.boundlessdeck/mcp.json` when a workspace opens and, only with the 项目级配置 setting on (`d.projectMCP`, off by default), merges `.mcp.json`, `.cursor/mcp.json`, `.vscode/mcp.json`, and loads the servers they declare; `mcpglobal.go` is the global install: the active-deck registry (`active-deck.json` under `os.UserConfigDir()/BoundlessDeck`, written by `startMCP`, cleared by `stopMCP`; tests point it elsewhere in `TestMain`) and the agents' user-level configs (`mcpAgents`: Claude Code, Claude desktop, Cursor, VS Code) it installs `mcp-stdio` into, never rewriting one that will not parse; `mcpbridge.go` is the stdio bridge: `boundlessdeck mcp-stdio --workspace DIR` (project configs) or with no workspace (global configs), which follows the active deck, re-reading it when the deck does not answer, and answers the handshake and lists itself while none is open.
- `settings.go` — the 设置 window (macOS: app menu → 设置… ⌘, as Finder has it; elsewhere 文件 → 设置… Ctrl+,): install/remove the global MCP per agent (statuses read off the UI thread), the 项目级配置 switch (`appSettings`, `settings.json` in the user-data dir) and removing the open deck's project configs.
- `titlebar.go` — on macOS the window has no title bar (`mygo.TitleBarHidden`; on Windows `windowTitleBar` keeps the system's, whose buttons would otherwise cover the toolbar): content runs under the traffic lights, placed level with the deck's top row (`trafficLights`, `chromeTop`); top-left chrome starts at `chromeLeft`. A `dragBand` as tall as `c.TitleBar().Height` drags the window: on the deck it lies under the block layer, which is `PassThrough` (otherwise the full-window layer box is the topmost hit and no press reaches the band), and the canvas declines left presses in it (`d.dragBand`), so only empty canvas there drags. Headless tests cannot observe a window drag starting.
- `zoomlayer.go` — the scaled block layer while a zoom gesture goes on (see "Real zoom" below). `textfonts.go` — `fontEpoch`: works around MyGo v0.7.4 freeing all CTFonts past 512 while the terminal plugin still draws glyphs of them; terminals get a new font key when it happens.
- `internal/word` — `.docx` → Markdown (`word.Read`, `word.Doc{Markdown, Media}`) in pure Go (headings, also hand-sized bold ones; bold/italic; bullet and numbered lists via numbering.xml; links; tables; pictures kept by name); `.doc` goes through macOS `textutil -convert docx` first. Literal `[`, `]`, `$` are written as character references: `\[…\]` would read as math.

Key design constraints (explained in `docs/requirements.md` §2):

- **Real zoom at rest, scaled mid-gesture.** `ui.WebView` can't be scaled, so the canvas multiplies block X/Y/W/H (and font sizes) by a camera's scale and lays blocks out at it: text/editors/terminals stay crisp. While a pinch or ⌘-wheel zoom goes on (`zoomGesture`), the blocks keep the layout camera `d.lay` and their layer is GPU-scaled by `cam.S/lay.S` (`zoomlayer.go`): no text is shaped or rasterized anew per step. Nothing is laid out mid-gesture, however far it zooms: a zoom renders the frame before it and, once it rests (150 ms), the frame after it. At rest the camera is on a **zoom level** (12 per doubling, 1 among them; `zoomLevel`): a zoom resting between levels glides to the nearest over 120 ms (`d.snap`, GPU-scaled, laid out once at the level), the keys step 3 levels (`zoomStep`), fit-all takes the level at most its fit. Laid out at repeated scales, text reuses fonts and cached glyphs; laid out at any scale, every rest re-rasterized all glyphs in view (the hitch) and piled up fonts toward MyGo's 512 limit. So view code inside the layer uses `d.lay`, never `d.cam`; block handlers get layer coordinates and wheel deltas and take them to the window with `layerToWindow` before world math; the grid, marquee and canvas input use `d.cam`. Keyboard zoom and fit-all lay out at once.
- **Immediate mode.** The whole tree rebuilds every frame. Only blocks the window shows some of (their tape and shadow included, `blockReachTop`/`blockReachSide`) are built (`visible`); one out of view builds nothing and asks for no load. In a 块堆 only the cards whose face shows (`faceShows`: the pushed-out card, the front one) load and lay out their content; the others draw just their header, and the queue ranks a stacked block's loads by its stack's place, and below `lodScale` (0.3) a block shows just its frame and title — no editor/terminal/bitmap. Crossing it, the content blurs away or comes clear from a blur over `contentFade` (`contentShown`/`fadeContent` in `blocks.go`); coming, it is built at once, fully blurred, so it can load meanwhile. Heavy state lives in `block.rt`, never in view locals.
- **The block worked in is the app's, not MyGo's focus.** MyGo moves the keyboard focus on every press: to nothing where nothing pressed takes it, and to nothing on a click into a web page (`webViewPress`: the native view has the keyboard). So `d.active` is the block worked in: `trackActive` (each frame) takes it from `d.focusBlock`'s owner (`focusOwner`: content `n.ID`, `addressFocus`, `cardFocus`) and keeps it while the focus is nowhere; only a press on the canvas, or `onBlockInput` on another block, ends it. `bodyCover` stays off for `d.active`, so a page clicked into keeps the wheel. Each card (stacks aside) is a `FocusBind` member, `cardFocus(n)`, so a press on its title or bar keeps the focus in it; the browser's bar buttons are `KeepFocus`.
- **One handler per press.** A press goes to the innermost handler (editor/terminal take clicks inside them); wheel/zoom events walk the chain, so blocks forward wheel and pinch back to the canvas so scrolling over a block still moves the canvas.
- **Threading.** File reads, image decoding, terminal start and dialogs (`mygo.Dialog.Open`) run in goroutines; results come back via `win.Update`. No I/O inside view code. A block's loads (text, image, document, PDF open/page, memo, terminal, web view) go through the deck's load queue (`loadqueue.go`): view code calls `d.wantLoad(key, n, start, work)` each frame it still wants one; at the end of the view `runLoads` drops what no card asked for this frame and starts the ones nearest the middle of the view (distance to the card, then to its middle), at most `loadLimit` (3) at a time. Mark a load under way in `start` (it runs as the load starts, not as it is asked for), and check generations in what `work` returns. In tests they run synchronously, in that order (`d.loads.started`).
- **Undo.** `addBlock`/`removeBlock` are the only ways a block enters or leaves the deck, so every addition/removal is undoable. Moving blocks through the MCP and laying them out go through `applyPlacements`, which records the before/after boxes as one `changeMoves`; an undo puts the whole layout back (dragging a block by hand is not recorded). Removing a block hangs up its terminal; an undone-back block starts a new one.
- **MCP is the workspace's, and its schema has one source.** Opening a deck starts the endpoint and makes it the active deck the global bridge follows (project-scoped MCP configs only when the setting asks); every write goes through the deck's own add/remove/undo/save path, on the UI thread (`onUI`). Adding a field to `block` means adding it to `mcpFields`; a reflection test enforces it. Project and user configs are merged, never replaced: a user's servers and keys stay.
- **Persistence.** A deck lives in its folder at `.boundlessdeck/deck.json`, written atomically (tmp + rename) when the deck closes (going home, opening another folder, closing the window). The folder is the deck's root: terminals start there and file paths inside it are stored relative to it (`linkPath`), so the folder can move.

Tests drive the real view headlessly with `ui.NewTester` (`Pinch`, `Wheel`, `Press`/`Move`/`Release`, `Image`); `testDeck(t)` in `canvas_test.go` gives a deck with a temp root and two notes.
